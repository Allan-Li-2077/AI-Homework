# 第十五周作业：可下发 Sub-Agent 的 Agent（Orchestrator）

## 一、作业目标

实现一个**编排器（Orchestrator）agent**：它自己不直接操作文件或计算，而是通过
`dispatch_agent` 工具把子任务委派给专门的 **sub-agent** 完成。每个 sub-agent 拥有
独立上下文、专属 system prompt 和受限工具集，跑完自己的 function-calling 循环后
**只把最终答案回传给主 agent**。

这是第十三周「渐进式披露 + SKILL」的自然延伸：第十三周让模型按需加载 SKILL 指令，
本周让模型按需**派生独立的子 agent** 去执行——对应 opencode 的 `task` 工具。

## 三、核心概念：为什么要 sub-agent

| 维度 | 单层 agent（直接给主 agent 所有工具） | Orchestrator + Sub-Agent |
|------|-----------------------------------|------------------------|
| 上下文 | 所有工具调用、观测都进主 agent 对话，撑爆 token | sub-agent 的中间过程留在自己上下文，主 agent 只收最终答案 |
| 专精 | 一个 prompt 干所有事，易顾此失彼 | 不同 `subagent_type` 有不同 prompt + 工具，边界清晰 |
| 并行 | 工具串行调用 | 主 agent 一次可派多个 sub-agent 并行（线程池） |
| 隔离 | 工具出错污染主上下文 | sub-agent 失败只影响子任务，主 agent 可重试/换策略 |
| 权限 | 主 agent 拥有所有工具 | sub-agent 只拥有它需要的工具（最小权限） |

省 token 的关键：sub-agent 的「思考 + 工具调用 + 观测」全部留在它**自己的**
`messages` 里（`run_subagent` 内部新建，函数外不可见），主 agent 只看到一行最终答案。

## 四、架构

```
用户提问
   │
   ▼
┌───────────────────────────────────────────┐
│ 主 Agent（Orchestrator）                   │
│  system prompt = 编排指令 + sub-agent 目录  │
│  唯一工具：dispatch_agent(task, type)       │
└───────────────────────────────────────────┘
   │
   │  模型判断：要不要委派？
   │
   ├─ 通识问题 → finish_reason=stop → 直接回答
   │
   └─ 需要探索/计算 → dispatch_agent(...)
                        │
                        ▼
          ┌──────────────────────────────────┐
          │ Sub-Agent（独立上下文）           │
          │  - 专属 system prompt            │
          │  - 受限工具集（schemas_for）       │
          │  - 自己的 function-calling 循环   │
          └──────────────────────────────────┘
                        │
                        │  list_files / search / read_file / calculator
                        │  （中间观测留在这里，不外泄）
                        ▼
                  最终答案（字符串）
                        │
                        ▼
          作为 tool result 回到主 agent
                        │
                        ▼
          主 agent 综合所有 sub-agent 答案 → 给用户回答
```

## 五、关键代码说明

### 5.1 Sub-Agent 配置（数据驱动，易扩展）

```python
@dataclass
class SubAgentConfig:
    name: str
    description: str
    system_prompt: str
    tools: list[str]           # 受限工具集

SUBAGENTS = {
    "explore": SubAgentConfig(
        name="explore",
        description="只读的代码/文件研究员……",
        tools=["list_files", "search", "read_file"],   # 没有 calculator、没有写工具
        system_prompt="你是一个只读的研究助手……",
    ),
    "general": SubAgentConfig(
        name="general",
        description="通用助手，可读文件和做算术……",
        tools=["list_files", "search", "read_file", "calculator"],
        system_prompt="……所有数字运算必须用 calculator 工具……",
    ),
}
```

新增一种 sub-agent 只需在 `SUBAGENTS` 里加一项，编排器自动发现并放进目录。

### 5.2 dispatch_agent 工具（主 agent 唯一工具）

```python
def build_dispatch_tool():
    return [{
        "type": "function",
        "function": {
            "name": "dispatch_agent",
            "description": "把一个子任务委派给 sub-agent……",
            "parameters": {
                "type": "object",
                "properties": {
                    "task": {"type": "string"},
                    "subagent_type": {"type": "string", "enum": list(SUBAGENTS.keys())},
                },
                "required": ["task", "subagent_type"],
            },
        },
    }]
```

主 agent 一次回复里可以多次调用 `dispatch_agent`，实现并行委派。

### 5.3 Sub-Agent 独立循环（关键：上下文隔离）

```python
def run_subagent(config, task, model=None, max_steps=6):
    client, model = get_llm_client_and_model(model)
    if client is None:
        return run_subagent_mock(config, task)        # 无 Key 走规则引擎

    # ★ messages 在函数内新建，主 agent 看不到这里的中间过程
    messages = [
        {"role": "system", "content": config.system_prompt},
        {"role": "user", "content": task},
    ]
    tools = schemas_for(config.tools)                # 只暴露该 sub-agent 允许的工具

    for step in range(1, max_steps + 1):
        resp = client.chat.completions.create(
            model=model, messages=messages, tools=tools,
            tool_choice="auto", temperature=0,
        )
        msg = resp.choices[0].message
        if resp.choices[0].finish_reason == "stop" or not msg.tool_calls:
            return msg.content                        # ★ 只回传最终答案

        messages.append(msg)
        for tc in msg.tool_calls:
            obs = call_tool(tc.function.name, json.loads(tc.function.arguments))
            messages.append({"role": "tool", "tool_call_id": tc.id, "content": obs})
    return "（sub-agent 达到最大步数）"
```

### 5.4 并行委派

```python
def execute_dispatch_parallel(dispatches, model=None):
    if len(dispatches) == 1:
        return {dispatches[0]["call_id"]: execute_dispatch(...)}

    with ThreadPoolExecutor(max_workers=min(len(dispatches), 4)) as pool:
        futures = {pool.submit(execute_dispatch, d["task"], d["subagent_type"], model): d["call_id"]
                   for d in dispatches}
        return {fut_to_cid[fut]: fut.result() for fut in as_completed(futures)}
```

主 agent 一次回复里调用 N 次 `dispatch_agent` → `execute_dispatch_parallel` 并行跑 N 个
sub-agent → 各自的最终答案作为 tool result 回灌。

### 5.5 主 Agent 循环

```python
def run_orchestrator(user_query, model=None, max_steps=6):
    messages = [
        {"role": "system", "content": build_orchestrator_system_prompt()},  # 仅 sub-agent 目录
        {"role": "user", "content": user_query},
    ]
    tools = build_dispatch_tool()

    for step in range(1, max_steps + 1):
        resp = client.chat.completions.create(model=model, messages=messages, tools=tools, ...)
        msg = resp.choices[0].message
        if resp.choices[0].finish_reason == "stop" or not msg.tool_calls:
            print(msg.content); return             # 直接回答

        messages.append(msg)
        dispatches = [parse(tc) for tc in msg.tool_calls]   # 收集本轮所有委派
        answers = execute_dispatch_parallel(dispatches, model)  # 并行执行
        for cid, ans in answers.items():
            messages.append({"role": "tool", "tool_call_id": cid, "content": ans})
```

## 六、Mock 模式（无 API Key 也能完整跑通）

无 Key 时自动走 mock，且 **sub-agent 用规则引擎真正干活**（而非假装）：

- `run_subagent_mock` 依据任务关键词驱动真实工具调用：
  - 「列出/有哪些文件/目录」→ `list_files` + `read_file`
  - 「搜索/查找/包含」→ `search`（自动提取引号内关键词或回退默认 pattern）
  - 「看看/读取 xx.md」→ `read_file`（自动提取文件名）
  - 「算/计算」→ `calculator`（自动提取算术表达式）
- `run_orchestrator_mock` 依据问题特征决定委派：
  - 复合任务（既要探索又要算）→ 拆成两个自包含子任务，**并行**委派 explore + general
  - 纯探索 → 单委派 explore
  - 纯计算 → 单委派 general
  - 通识问题 → 不委派，直接回答

这样 mock 模式也能 end-to-end 展示「委派 → 工具 → 结论 → 综合」全流程。

## 七、安全设计

- **工具沙箱**：`calculator` 用 AST 白名单做安全求值，不使用 `eval`/`exec`，
  实测拒绝 `__import__(...)` 等注入。
- **路径归一**：`read_file`/`list_files`/`search` 通过 `_resolve()` 把相对路径
  归一到 `workspace/` 下，sub-agent 无法越权读写源码。
- **最小权限**：`explore` 只有只读工具，`general` 才有 calculator，互不越界。

## 九、与第十三周的对比

| 维度 | 第十三周（SKILL 渐进式披露） | 第十五周（Sub-Agent 委派） |
|------|------------------------|------------------------|
| 加载对象 | SKILL 指令（一段 Markdown） | 一个独立 agent（带循环+工具） |
| 工具 | `load_skill(name)` 返回 body | `dispatch_agent(task, type)` 启动 agent |
| 上下文 | SKILL body 进入主对话 | sub-agent 有独立对话，主对话只收答案 |
| 执行能力 | 主 agent 按 SKILL 指令执行 | sub-agent 自主多步执行 |
| 并行 | 否（一次加载一个 SKILL） | 是（一次可派多个 sub-agent） |

## 十、总结

1. **编排器**：主 agent 唯一工具是 `dispatch_agent`，强制它学会「委派」而非亲力亲为。
2. **上下文隔离**：sub-agent 在 `run_subagent` 内部新建 messages，中间过程不外泄，
   主 agent 上下文不被工具观测撑爆——这是省 token 的核心。
3. **可专精 + 最小权限**：不同 `subagent_type` 有不同 prompt 与工具集，`explore` 只读、
   `general` 才能算，能力边界清晰。
4. **可并行**：主 agent 一次回复多次调用 `dispatch_agent`，线程池并行执行。
5. **开箱即跑**：无 API Key 时 mock 模式下 sub-agent 用规则引擎真干活，完整展示委派流程。
