# 作业说明：图编排 Supervisor —— 确定性路由的 subagent 并行系统

**作业题目**：自己实现一个可以下发 subagent 的 agent，并行完成多项工作
**对应课程**：Week15「知识图谱 × 大模型」Part 6 · Graph Engineering（PPT P19-P21）

## 0. 一句话定位

主 agent（Supervisor）用**确定性 Python 规则**完成路由（教程 P20「代码定边」），把复合任务拆给多个**异构 worker**（行业研究员 / 数据分析师 / 文案写手）**并行执行**（LLM 只在节点内干活），再 fan-in 聚合成单一成品交付。并行收益用「并行 vs 串行」A/B 真实量化。

```
                        ┌─ res_1 行业研究员（ReAct + web_search/知识）
用户问题 → route() 定边 ──┤                                    ↘
                        └─ dat_1 数据分析师（ReAct + calculator）→ wri_1 文案写手（依赖两者）→ 成品交付
                        （stage1 并行 fan-out，墙钟≈max）        （stage2 fan-in + 聚合）
```

## 1. 对照 P19：Graph Engineering 结构化的是「系统本身」

- 本项目的「图」是什么：**节点** = supervisor + 3 类异构 worker；**边** = 派发边（supervisor→worker，代码路由决定）+ 依赖边（res/dat→writer，数据流）+ 回收边（结果回 supervisor）
- 与 GraphRAG 的区别：GraphRAG 结构化**数据**（实体/关系/三元组，回答「系统知道什么」）；本项目结构化**系统**（agent 拓扑与路由，回答「系统是谁」）
- 五层栈定位：本作业聚焦 **L5 Graph Engineering（多 agent 拓扑）**；节点内沿用 week12 学的 L4 Loop Engineering（手写 ReAct），是 L4→L5 的自然进阶

## 2. 对照 P20：拓扑选择与「代码定边、模型定节点内」

### 2.1 拓扑：Orchestrator-Workers + Diamond（fan-out/fan-in）+ 依赖边

- 主演示题是 **Diamond**：并行多专家（研究员+分析师）→ 聚合（写手）
- 纯依赖链题是 **Pipeline 元素**：researcher → writer 顺序执行
- supervisor 派发回收是 **Orchestrator-Workers**

### 2.2 「代码定边」的落地证据（路由是确定性 Python，LLM 零参与）

`router.py` 的 `route(question)` 是纯函数：关键词规则命中 worker 类别 → 生成 TaskPlan（stages/edges/依赖关系）。**整张图在第一条 LLM 调用之前就完全已知**，三个证据：

1. **可离线单测**：`python src/router.py` 不花一分钱 LLM 调用，验证四条路由路径（问候直答 / 单 worker / 两阶段 DAG / 纯依赖链）
2. **plan 事件预画图**：前端收到 plan 事件时一次性画出含依赖边的完整 DAG，而不是等节点运行时才生长（旧项目是 LLM 派发时才长节点）
3. **route_note 可审计**：每次路由都输出人类可读的决策说明（「命中 行业研究员、数据分析师、文案写手 关键词 → stage1 并行 fan-out…」）

### 2.3 「模型定节点内」的落地

LLM 只在节点内干活：研究员 ReAct 查资料、分析师 ReAct 按计算器、写手单次调用成稿。LLM 不参与决定「派不派、派给谁」。

### 2.4 与旧项目（LLM 自主路由）对比

| 维度 | 旧项目 market_research_subagents | 本项目 graph_supervisor |
|------|--------------------------------|------------------------|
| 路由 | 主 agent ReAct 思考决定（LLM 定边） | `route()` 纯 Python 规则（代码定边） |
| 拓扑 | 运行时生长（dispatch 时才加节点） | 路由后完全已知（plan 预画） |
| 稳定性 | 踩过「不派发/自己串行搜 8 次」的坑 | 同输入永远同图，可复现可测试 |
| worker | 同构（都只有 web_search） | 异构（搜索/计算器/纯创作三套工具集） |
| 拓扑形态 | 星形 | 星形 + 依赖边（DAG） |

## 3. 对照 P21：落地要点逐条

| 教程要点 | 本项目落地 |
|---------|-----------|
| **Schema-first 交接** | 主→子 `TaskPlan`（stages/edges/task_prompt/depends_on 字段契约）；子→主 `NodeResult`（node_id/status/content/structured/trace/duration）。下游投喂从结构拼装，不裸传原始输出 |
| **模型分层** | 路由层零 LLM 成本（纯规则）；调研/计算 temperature 0.0 + ReAct；写手 temperature 0.7 + 单次调用 |
| **节点级可观测** | 每次运行生成 graph_id，节点事件带 node_id；每节点全量 trace（Thought/Action/Observation）；SSE 节点级事件流 |
| **状态可恢复** | `--save-trace` 落盘 `outputs/trace_<graph_id>.json`（计划+每节点 trace+统计），可回放审计，无数据库 |
| **并行分支收益** | ThreadPoolExecutor 并行，分阶段 wall_clock vs serial_sum 量化（见 §4） |

## 4. 并行收益量化 + Amdahl 诚实解读

**指标定义**：
- **fan-out 段加速** = 阶段内 serial_sum / wall_clock（子任务并行纯收益）
- **端到端加速** = 全图串行墙钟 / 并行墙钟（含依赖边与聚合段的串行开销）

**A/B 真实数据**（`python src/eval_compare.py`，2026-08-14 跑出，同一题 parallel 与 serial 各跑一次）：

| 题 | 形态 | 并行墙钟 | 串行墙钟 | fan-out 加速 | 端到端加速 |
|----|------|---------|---------|-------------|-----------|
| 1 咖啡调研+计算+推文 | 三 worker 复合 | 20.30s | 29.88s | **1.61×** | **1.47×** |
| 2 扫地机器人调研+计算 | 双 worker 全并行 | 17.29s | 21.92s | 1.43× | 1.27× |
| 3 科普推文（先调研） | 纯依赖链（反例） | 18.38s | 17.78s | 1.0× | **0.97×** |
| **平均** | | **18.66s** | **23.19s** | **1.35×** | **1.24×** |

**解读**：
- 题 1 fan-out 加速最高（1.61×）：研究员+分析师串行要 19.45s，并行墙钟 12.05s——两个独立子任务的墙钟从 sum 压到 ≈max
- 题 1 端到端（1.47×）低于 fan-out（1.61×）：stage2 写手必须等 stage1 全部完成，依赖边和写手成稿段串行（Amdahl 定律现场）
- 题 3 加速 0.97×（≈1）：fan-out 段只有 1 个节点，**没有可并行分支就没有并行收益**——正面印证 P21「纯顺序任务，图反而降性能」（Nature MI：顺序任务降 1.2~12.8%，本实验 0.97× 与之一致）
- 诚实结论：并行收益只落在**可并行的子任务段**；依赖边、聚合段、supervisor 串行开销是总加速比的天花板

## 5. 与旧项目 market_research_subagents 的演进关系

**复用**：通用 ReAct 引擎（react_loop）、极简 LLM 客户端、Tavily 零依赖搜索、SSE queue 桥接模式、并行统计口径（wall_clock vs serial_sum）、深色拓扑可视化语言。

**改变**（三个核心升级）：
1. LLM 自主路由 → **确定性路由**（代码定边，教程原则落地）
2. 同构调研员 → **异构 worker + 依赖边**（对应「并行完成多项工作」：不同 worker 干不同活）
3. dispatch 时生图 → **plan 时预画整张 DAG**（路由确定性带来的可观测性红利）

## 6. 踩坑记录

| # | 问题 | 根因 | 解法 |
|---|------|------|------|
| 1 | 分析师报 KeyError '"calc_steps"' | 自定义 prompt 含 JSON 块，`str.format(tools_desc=…)` 把花括号当占位符 | 改用 `replace("{tools_desc}", …)` 注入，对花括号免疫 |
| 2 | 分析师不调 calculator，自由发挥直接出答案 | 自定义 worker prompt 替换了默认 REACT_SYSTEM，LLM 没见过 ReAct 格式说明和工具列表 | 格式契约归引擎统一追加：`角色prompt + REACT_FORMAT(含工具列表)`，worker prompt 只管角色 |
| 3 | SSE 流在 plan 事件处崩（function 不可序列化） | plan 事件入队后，执行线程又往节点 dict 注入 cfg（含函数对象），跨线程共享可变状态 | 执行用 `copy.deepcopy(plan["stages"])`，plan 保持干净 |
| 4 | 分析师算完同比被强制收尾，没出 CAGR | max_steps=4 不够分步计算 + Final Answer 的轮次 | 分析师 max_steps=6 + prompt 引导「算完立即 Final Answer」 |
| 5 | Windows 控制台中文乱码 | Python 默认 GBK 编码输出 | 入口 `sys.stdout/stderr.reconfigure(encoding="utf-8")` |
| 6 | 错误节点 duration 未赋值 UnboundLocalError | 异常分支漏赋值 | except 分支补 duration 计算 |

（更早的旧项目还踩过 7 条坑——system_prompt 定义了没传、空 action 撞 max_steps、长 observation 撑爆 context、SSE 跨线程、Tavily 失败兜底等——本项目在架构上已全部规避：显式传 system_prompt、解析兜底、截断投喂、queue 桥接、错误降级）

## 7. 复现步骤

```bash
cd graph_supervisor
pip install -r requirements.txt
export DEEPSEEK_API_KEY="sk-xxx"      # 必填
# export TAVILY_API_KEY="tvly-xxx"    # 可选：不设则研究员走知识模式

python src/router.py                  # ① 确定性路由单测（零 LLM 成本，四条路径）
python src/workers.py                 # ② calculator 白名单自测（含注入拒绝）
python src/executor.py                # ③ stub 并行自测（假节点验证墙钟≈max）
python src/cli.py                     # ④ CLI 主演示：调研+计算+推文
python src/cli.py --demo direct       #    直答审批门（零派发）
python src/cli.py --demo chain --serial  # 串行对照
uvicorn src.serve:app --port 8003     # ⑤ Web 可视化 http://localhost:8003
python src/eval_compare.py            # ⑥ A/B 量化 → outputs/eval_compare.json
```
