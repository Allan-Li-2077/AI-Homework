# 项目分析 Skill

## 目标

在较低文件读取量、较少上下文和较少外部调用的前提下，建立对陌生代码库可靠、可行动的理解。本版本不仅回答“项目是什么”，还回答：

- 用户问题会经过哪些模块；
- 某个需求应该看或改哪些文件；
- 结论如何验证；
- 为得到这些结论读取了什么、跳过了什么、消耗可能集中在哪里。

优先使用项目中的代码、配置和文档作为证据，不要凭经验猜测。本 Skill 负责项目熟悉、需求定位、效率控制和验证设计，不负责修改项目文件；只有用户明确提出后续实现要求时，才进入编码流程。

## 分析模式与深度

根据用户问题选择模式，并在报告开头说明模式和深度：

| 模式 | 适用问题 | 默认深度 |
|---|---|---|
| 项目概览 | “这个项目是做什么的？” | 快速 |
| 请求追踪 | “一个请求如何得到最终结果？” | 标准 |
| 需求定位 | “这个功能应该改哪些文件？” | 标准 |
| 实现对比 | “原生版和框架版有什么区别？” | 标准 |
| 运行验证 | “怎么启动、测试和确认结果？” | 标准 |

深度规则：

- `快速`：只读取项目说明、依赖配置、目录结构和入口文件，适合先建立地图。
- `标准`：在快速基础上读取入口的直接依赖、核心流程和相关测试/评估文件。
- `深入`：只有用户明确要求或问题涉及关键风险时，才读取更多边界模块、历史记录和多套实现。

用户没有指定深度时，默认使用标准深度。不要因为“熟悉项目”就自动完整读取所有源码。

## 效率与成本控制

### 1. 先设定分析预算

开始前根据问题确定预算，不需要向用户展示内部 token 数字，但要在报告中记录实际范围：

```text
分析目标 -> 所需证据 -> 最小文件集合 -> 是否需要深入
```

优先保证结论可靠，再减少无关读取。不要为了省 token 跳过入口、配置或直接依赖这些高价值文件。

### 2. 按信息价值读取

默认按以下顺序读取：

1. 项目约束、README、架构说明和运行指南；
2. 依赖清单、环境配置和启动脚本；
3. 服务、CLI、任务或应用启动入口；
4. 入口直接调用的核心模块；
5. 测试、评估和示例数据；
6. 只有在结论仍不完整时才读取外围模块、历史日志和生成文件。

先用目录列表和关键词搜索定位候选文件，再读取完整内容。不要先把大型源码、JSON、PDF、模型文件或生成目录全部加载进上下文。

### 3. 避免重复工作

- 维护已检查文件清单；同一轮分析中不要重复完整读取同一个文件。
- 已经由报告或前一步确认的事实，除非发现矛盾，不要重新搜索。
- 同时读取多个相互独立的小文件时，优先并行获取，减少等待和重复上下文说明。
- 对大型文件先搜索相关符号或章节，只读取命中的上下文；只有主流程无法闭合时才扩展范围。
- 不要把依赖库内部源码当作项目源码分析，除非用户明确询问该依赖的行为。

### 4. 控制外部调用和运行成本

- 静态分析阶段默认不调用 LLM、Embedding、数据库、网络 API 或远程服务。
- 用户要求运行验证时，先执行无副作用的轻量检查，再做单个 smoke query，最后才考虑完整评估。
- 不要默认运行完整 RAGAS、全量 Embedding、批量下载或全量回归；这些操作可能产生 API 费用、长时间运行或大量 token 消耗。
- 需要评估时优先使用少量代表性题目，并说明采样范围、外部调用次数和未覆盖内容。
- 不要为了证明一个静态结论启动长期服务。

### 5. 控制报告长度

- 结论优先，避免复述已经引用的长文档内容。
- 只展开与用户问题有关的调用链；无关模块用一句话归纳。
- 大型目录使用摘要和数量，不罗列所有文件。
- 空的报告章节写“未发现”或合并掉，不制造无信息段落。
- 重要结论保留路径和行号，路径本身就是证据，不需要复制整段代码。

## 执行流程

### 1. 确认范围和约束

- 根据用户提供的路径或当前工作目录确定项目根目录。
- 如果用户只给出 `src` 子目录，向上检查相邻的配置、文档、数据和评估目录。
- 优先读取项目级说明和约束，包括 `AGENTS.md`、`README.md`、贡献指南和配置说明。
- 记录分析范围、选择的模式、深度和排除项。

### 2. 建立项目地图

- 列出顶层目录和重要文件。
- 默认跳过 `.git`、`node_modules`、`.venv`、`venv`、`__pycache__`、`dist`、`build`、大型输出目录和模型权重。
- 区分源码、测试、配置、数据、文档和脚本目录。
- 使用快速搜索定位入口、命令、路由、类、函数和用户问题中的关键词。
- 对多套实现先建立映射，例如“原生版 -> `src/`”“框架版 -> `src_langchain/`”。

### 3. 识别运行环境

检查项目实际存在的配置文件：

- Python：`pyproject.toml`、`requirements.txt`、`setup.py`、`Pipfile`
- JavaScript 或 TypeScript：`package.json`、锁文件和构建配置
- Java：`pom.xml`、`build.gradle`
- Go：`go.mod`
- Rust：`Cargo.toml`
- 容器项目：`Dockerfile`、`docker-compose.yml`

报告语言、框架、包管理器、重要依赖、入口命令、环境变量和外部服务，并区分：

- `已确认`：代码、配置或文档明确写出；
- `代码推断`：由导入或调用关系推断，但未实际运行；
- `待验证`：需要安装依赖、启动服务或访问外部系统才能确认。

### 4. 追踪主流程

- 从实际入口开始，例如服务路由、CLI 命令、定时任务、应用启动函数或测试入口。
- 跟踪用户输入经过的关键函数、类和模块，直到最终输出、数据库写入、文件生成或外部调用。
- 每一步记录入口、调用目标、输入变化、输出变化和证据文件。
- 区分主流程、可选分支、异常分支和调试分支。
- 只有在代码或项目文档中有依据时，才能声称两个模块之间存在调用关系。

### 5. 做需求定位

当用户询问“某功能应该改哪里”时：

1. 找到用户输入进入系统的入口；
2. 找到承载业务规则或数据处理的核心模块；
3. 找到输出、持久化、接口或页面展示位置；
4. 找到相关测试、评估题或示例数据；
5. 列出直接相关、间接影响和暂不需要修改的文件；
6. 给出最小修改范围和验证问题，不直接修改代码。

先沿调用链定位，再按文件名补充搜索，避免把全仓库文件都列为相关文件。

### 6. 检查文档与代码一致性

交叉检查启动命令、依赖、默认配置、接口路径、模型名称和数据规模：

- 文档和代码一致：标记 `已确认`；
- 文档描述旧实现而代码已变化：同时报告两者，以当前代码为行为依据；
- 只有文档提到但代码中找不到：标记 `文档声明，代码未确认`；
- 代码存在但文档没有说明：标记 `代码存在，文档缺失`。

### 7. 设计验证方案

按成本从低到高排列验证：

1. 静态验证：文件、函数、配置和调用关系；
2. 轻量验证：帮助命令、导入检查或已有小测试；
3. 单样本运行：一个请求或一个代表性评估题；
4. 批量运行：完整评估、全量索引或全量回归，仅在用户明确要求时执行。

没有实际执行的命令标记为 `待验证`。记录预计会产生的网络调用、模型调用、时间成本或费用风险。

### 8. 输出报告

事实、结论、建议和待确认问题分开。重要结论附文件路径，代码级结论尽量附行号。报告末尾补充效率记录。

## 报告格式

```markdown
# 项目分析报告

## 1. 分析范围与模式
- 项目根目录：
- 分析模式：项目概览 / 请求追踪 / 需求定位 / 实现对比 / 运行验证
- 分析深度：快速 / 标准 / 深入
- 未覆盖范围：

## 2. 项目用途
说明项目解决的问题、主要使用者和核心输入输出。

## 3. 技术栈
| 项目 | 结论 | 状态 | 证据 |
|---|---|---|---|

## 4. 目录结构与实现映射
只列重要目录和文件。多套实现要说明对应关系。

## 5. 运行方式
每条命令标记：已确认 / 代码推断 / 待验证。

## 6. 核心入口
列出入口文件、函数、路由或命令，并说明触发方式。

## 7. 请求执行链路
对每一步列出：模块、关键接口、输入输出变化、证据。

## 8. 需求定位
如果用户提出具体需求，列出直接相关、间接影响、相关测试、暂不修改文件和最小修改范围。

## 9. 关键模块
| 文件 | 作用 | 关键接口 | 上游 | 下游 | 证据 |
|---|---|---|---|---|---|

## 10. 配置、依赖与数据
列出环境变量、外部服务、数据文件、生成文件和启动前置条件。

## 11. 文档与代码差异
| 项目 | 文档描述 | 代码行为 | 判断 | 证据 |
|---|---|---|---|---|

## 12. 测试与验证方案
列出验证目标、命令、当前状态、外部调用和成本风险。

## 13. 风险与待确认问题
区分已确认风险、文档缺口、代码推断和待验证问题。

## 14. 建议阅读或修改顺序
按照入口、主流程、领域模块、测试和配置给出顺序。

## 15. 效率记录
- 扫描目录或文件数量：
- 完整读取的关键文件：
- 仅搜索或摘要读取的文件：
- 跳过的目录或大文件：
- 外部服务或模型调用次数：
- 预计主要成本来源：
- 可进一步节省的地方：

## 16. 结论
用几句话总结项目当前状态和最重要的下一步。
```

## 证据规则

- 环境提供项目绝对路径时，使用绝对路径；否则使用清晰的项目相对路径。
- 涉及具体代码的结论，在条件允许时附上行号。
- 没有找到文件、命令、测试或配置时，明确写“未找到”。
- 没有实际执行或确认的命令和结论，明确写“待验证”。
- 不要编造架构分层、接口行为、环境变量、调用关系或测试结果。
- 不要把历史日志中的成功结果当成本次运行结果，应注明来源和时间。
- 不要隐藏文档和实现之间的矛盾；同时报告两者，并说明哪一方更可能代表当前行为。
- 证据不足时降低结论强度，使用“可能”“推断”或“待确认”。
- 效率记录只能报告实际观察到的读取、搜索和调用范围，不要伪造 token 数、耗时或费用。

## 使用边界

- 这是项目分析、需求定位、效率控制和验证设计流程，不是功能实现流程。
- 分析过程中不要编辑、删除、重命名或生成目标项目文件。
- 不要安装依赖、启动长期服务或访问外部系统，除非用户明确要求验证。
- 不要把简短概览扩展成所有文件的无差别罗列。
- 如果项目过大，应说明已经检查的内容和未覆盖的范围。
- 不要因为发现风险就自动修复；先把风险和建议验证步骤写入报告。

## 示例

### 示例一：快速项目概览

用户请求：

> 帮我快速看懂这个项目，尽量少消耗 token。

应执行：

1. 读取项目说明、依赖配置和顶层目录；
2. 定位入口文件；
3. 只读取入口和一层直接依赖；
4. 输出主要模块、主流程和未覆盖范围；
5. 在效率记录中说明跳过了哪些大目录。

### 示例二：需求定位

用户请求：

> 我想给这个 RAG 项目增加按年份过滤，应该改哪些文件？

应执行：

1. 定位查询入口和请求参数模型；
2. 追踪过滤条件进入向量检索、关键词检索、融合和调试接口的路径；
3. 查找已有测试或评估数据；
4. 给出最小修改范围和验证问题；
5. 不执行全量评估，不直接修改代码。

### 示例三：需要模型调用的验证

用户请求：

> 验证这个 RAG 项目效果，并尽量控制成本。

应执行：

1. 先做静态和依赖检查；
2. 选 1 道代表题做 smoke query；
3. 只有用户确认后才扩展到小样本评估；
4. 明确完整 RAGAS、全量 Embedding 和批量 API 调用未执行。

## 版本说明

`2.0.0` 在原有第二版能力的基础上加入执行效率和成本控制：分析深度分级、按信息价值读取、避免重复读取、外部调用分级、报告长度控制和效率记录。

当前版本仍不包含自动修改代码、自动安装依赖、自动启动服务或自动生成回归测试。
