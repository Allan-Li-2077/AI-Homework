# 项目分析 Skill

## 目标

建立对陌生代码库可靠、可行动的理解。第一版主要回答“项目是什么”；本版本还要回答“用户的问题会经过哪些模块”“某个需求应该看或改哪些文件”“结论如何验证”。

优先使用项目中的实际代码、配置和文档作为证据，不要凭经验猜测。本 Skill 负责项目熟悉、需求定位和验证设计，不负责修改项目文件；只有用户明确提出后续实现要求时，才进入编码流程。

## 分析模式

根据用户问题选择一个或多个模式，并在报告开头说明采用的模式：

| 模式 | 适用问题 | 主要产出 |
|---|---|---|
| 项目概览 | “这个项目是做什么的？” | 技术栈、目录、入口、主流程 |
| 请求追踪 | “一个请求如何得到最终结果？” | 输入到输出的调用链和数据流 |
| 需求定位 | “实现某功能应该改哪些文件？” | 相关文件、影响范围、修改边界 |
| 实现对比 | “原生版和框架版有什么区别？” | 模块映射、能力差异、选型取舍 |
| 运行验证 | “怎么启动、测试和确认结果？” | 环境条件、命令、验证步骤和未验证项 |

用户只要求概览时不要进行无关的深度追踪；用户提出具体需求时，优先使用“需求定位 + 请求追踪 + 运行验证”。

## 执行流程

### 1. 确认范围和约束

- 根据用户提供的路径或当前工作目录确定项目根目录。
- 如果用户只给出 `src` 子目录，向上检查相邻的配置、文档、数据和评估目录；这些目录可能决定源码如何运行。
- 优先读取项目级说明文件和约束，包括 `AGENTS.md`、`README.md`、贡献指南和配置说明。
- 记录本次分析范围，例如“分析原生版，不深入第三方依赖和生成文件”。

### 2. 建立项目地图

- 列出顶层目录和重要文件。
- 默认跳过 `.git`、`node_modules`、`.venv`、`venv`、`__pycache__`、`dist`、`build` 以及大型输出目录，除非用户要求分析它们。
- 区分源码、测试、配置、数据、文档和脚本目录。
- 使用快速搜索定位入口、命令、路由、类、函数和用户问题中的业务关键词。
- 对有多个实现的项目，先建立实现映射，例如“原生版 -> `src/`”“框架版 -> `src_langchain/`”。

### 3. 识别运行环境

检查项目实际存在的配置文件：

- Python：`pyproject.toml`、`requirements.txt`、`setup.py`、`Pipfile`
- JavaScript 或 TypeScript：`package.json`、锁文件和构建配置
- Java：`pom.xml`、`build.gradle`
- Go：`go.mod`
- Rust：`Cargo.toml`
- 容器项目：`Dockerfile`、`docker-compose.yml`

报告语言、框架、包管理器、重要依赖、入口命令、环境变量和外部服务。区分三种状态：

- `已确认`：代码、配置或文档明确写出；
- `代码推断`：由导入关系或调用关系推断，但未实际运行；
- `待验证`：需要安装依赖、启动服务或访问外部系统才能确认。

### 4. 根据用户问题追踪主流程

- 从实际入口开始，例如服务路由、CLI 命令、定时任务、应用启动函数或测试入口。
- 跟踪用户输入经过的关键函数、类和模块，直到最终输出、数据库写入、文件生成或外部调用。
- 对每一步记录：入口、调用目标、输入变化、输出变化和证据文件。
- 区分主流程、可选分支、异常分支和调试分支。
- 如果用户给出具体需求，沿着现有调用链定位最可能受影响的模块，而不是只按文件名猜测。
- 只有在代码或项目文档中有依据时，才能声称两个模块之间存在调用关系。

### 5. 做需求定位

当用户询问“某功能应该改哪里”时，按以下顺序定位：

1. 找到用户输入进入系统的入口。
2. 找到承载该业务规则或数据处理的核心模块。
3. 找到输出、持久化、接口或页面展示位置。
4. 找到相关测试、评估题或示例数据。
5. 列出可能需要修改的文件，并说明每个文件的职责和依据。
6. 列出不应修改的文件或暂时不在范围内的模块，避免扩大改动面。

不要在分析阶段直接修改文件。需求定位的输出是“修改范围建议”，不是实现结果。

### 6. 检查文档与代码的一致性

对启动命令、依赖、默认配置、接口路径、模型名称和数据规模进行交叉检查：

- 文档和代码一致时，标记为 `已确认`；
- 文档描述旧实现而代码已变化时，同时报告两者，并以当前代码为运行行为的主要依据；
- 只有文档提到但代码中找不到的能力，标记为 `文档声明，代码未确认`；
- 代码存在但文档没有说明的关键行为，标记为 `代码存在，文档缺失`。

### 7. 设计验证方案

列出能够验证结论的最小步骤：

- 静态验证：检查文件、函数、配置和调用关系；
- 轻量验证：运行不会修改数据的帮助命令、导入检查或已有测试；
- 运行验证：启动服务、执行查询或调用外部 API，仅在用户明确要求时执行。

没有实际执行的命令必须标记为 `待验证`。不要把项目文档中的命令写成已经成功运行的命令。

### 8. 输出报告

按照下方模板组织报告。事实、分析结论、建议和待确认问题要分开。重要结论附文件路径，代码级结论尽量附行号。

## 报告格式

```markdown
# 项目分析报告

## 1. 分析范围与模式
- 项目根目录：
- 本次分析模式：项目概览 / 请求追踪 / 需求定位 / 实现对比 / 运行验证
- 未覆盖范围：

## 2. 项目用途
说明项目解决的问题、主要使用者和核心输入输出。

## 3. 技术栈
| 项目 | 结论 | 状态 | 证据 |
|---|---|---|---|
| 编程语言 |  |  |  |
| 框架 |  |  |  |
| 包管理器 |  |  |  |
| 数据库或外部服务 |  |  |  |

## 4. 目录结构与实现映射
只列重要目录和文件。存在多套实现时，说明它们的对应关系。

## 5. 运行方式
给出安装、配置、启动和测试命令。
每条命令标记：已确认 / 代码推断 / 待验证。

## 6. 核心入口
列出入口文件、函数、路由或命令，并说明触发方式。

## 7. 请求执行链路
说明输入经过哪些模块到达输出。
对每一步列出：模块、关键接口、输入输出变化、证据。

## 8. 需求定位
如果用户提出了具体需求，输出：
- 直接相关文件；
- 间接影响文件；
- 相关测试或评估文件；
- 暂不需要修改的文件；
- 推荐的最小修改范围。

## 9. 关键模块
| 文件 | 作用 | 关键接口 | 上游 | 下游 | 证据 |
|---|---|---|---|---|---|

## 10. 配置、依赖与数据
列出环境变量、外部服务、数据文件、生成文件和启动前置条件。

## 11. 文档与代码差异
| 项目 | 文档描述 | 代码行为 | 判断 | 证据 |
|---|---|---|---|---|

## 12. 测试与验证方案
列出已存在的测试、建议命令、验证目标和当前状态。

## 13. 风险与待确认问题
区分已确认风险、文档缺口、代码推断和待验证问题。

## 14. 建议阅读或修改顺序
按照入口、主流程、领域模块、测试和配置给出顺序。

## 15. 结论
用几句话总结项目当前状态和最重要的下一步。
```

## 证据规则

- 环境提供项目绝对路径时，使用绝对路径；否则使用清晰的项目相对路径。
- 涉及具体代码的结论，在条件允许时附上行号。
- 没有找到文件、命令、测试或配置时，明确写“未找到”。
- 没有实际执行或确认的命令和结论，明确写“待验证”。
- 不要编造架构分层、接口行为、环境变量、调用关系或测试结果。
- 不要把历史日志中的成功结果当成本次运行结果，应注明来源和时间。
- 不要隐藏文档和实现之间的矛盾；同时报告两者，并说明哪一方更可能代表当前行为。
- 证据不足时降低结论强度，使用“可能”“推断”或“待确认”，不要伪装成确定事实。

## 使用边界

- 这是项目分析、需求定位和验证设计流程，不是功能实现流程。
- 分析过程中不要编辑、删除、重命名或生成目标项目文件。
- 不要安装依赖、启动长期服务或访问外部系统，除非用户明确要求验证。
- 不要把简短概览扩展成所有文件的无差别罗列。
- 如果项目过大，应说明已经检查的内容和未覆盖的范围。
- 不要因为发现风险就自动修复；先把风险和建议验证步骤写入报告。

## 示例

### 示例一：项目概览

用户请求：

> 帮我熟悉这个项目。

应执行：

1. 查找项目约束文件和运行环境配置。
2. 建立目录和实现映射。
3. 定位服务、CLI 或任务入口。
4. 说明主要流程和数据流。
5. 输出建议阅读顺序和待验证事项。

### 示例二：需求定位

用户请求：

> 我想给这个 RAG 项目增加按年份过滤，应该改哪些文件？

应执行：

1. 定位查询入口和请求参数模型。
2. 追踪过滤条件如何进入检索层。
3. 检查向量检索、关键词检索、融合和调试接口是否都处理该条件。
4. 查找已有测试或评估数据。
5. 给出最小修改范围和验证问题，不直接修改代码。

## 版本说明

`2.0.0` 在 `1.0.0` 的基础上增加了需求定位、请求链路追踪、多实现映射、文档代码差异检查和分级验证方案。

当前版本仍不包含自动修改代码、自动安装依赖、自动启动服务或自动生成回归测试。
