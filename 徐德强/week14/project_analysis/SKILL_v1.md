# 项目分析 Skill

## 目标

在提出修改建议之前，建立对陌生代码库可靠的理解。优先使用项目中的实际代码、配置和文档作为证据，不要凭经验猜测。本 Skill 负责项目熟悉和分析，不负责修改项目文件；只有用户明确提出后续实现要求时，才进入编码流程。

## 执行流程

根据用户问题的范围控制分析深度。按以下顺序执行：

### 1. 确认分析范围

- 根据用户提供的路径或当前工作目录确定项目根目录。
- 优先读取项目级说明文件和约束，包括 `AGENTS.md`、`README.md`、贡献指南和配置说明。
- 根据用户问题确定分析深度。用户只要求概览时，分析目录结构和主流程；用户询问具体功能时，重点分析相关模块及其直接依赖。

### 2. 建立项目地图

- 列出顶层目录和文件。
- 默认跳过 `.git`、`node_modules`、`.venv`、`venv`、`__pycache__`、`dist`、`build` 以及大型输出目录，除非用户明确要求分析它们。
- 区分源码、测试、配置、数据、文档和脚本目录。
- 使用快速搜索定位入口文件、命令定义、路由处理器、核心函数和重要业务关键词。

### 3. 识别运行环境

根据项目实际技术栈检查相关配置文件：

- Python：`pyproject.toml`、`requirements.txt`、`setup.py`、`Pipfile`
- JavaScript 或 TypeScript：`package.json`、锁文件和构建配置
- Java：`pom.xml`、`build.gradle`
- Go：`go.mod`
- Rust：`Cargo.toml`
- 容器项目：`Dockerfile`、`docker-compose.yml`

报告项目使用的语言、框架、包管理器、重要依赖、入口命令和环境变量。区分文件中明确记录的命令和根据惯例推断的命令。

### 4. 追踪主流程

- 从实际入口开始分析，例如服务路由、CLI 命令、定时任务、应用启动函数或测试入口。
- 跟踪重要调用进入服务层、领域层、存储层、模型层和展示层。
- 选择一个有代表性的输入，说明它如何经过系统处理并产生输出。
- 如果用户提出了具体功能需求，定位最可能需要修改的文件，并说明每个文件与需求的关系。
- 只有在代码或项目文档中有依据时，才能声称两个模块之间存在调用关系。

### 5. 检查运行条件

检查以下内容：

- 安装、启动和配置命令；
- 必需的环境变量和外部服务；
- 数据库初始化或迁移步骤；
- 测试、代码检查、格式化和构建命令；
- 文档与实现之间缺失或矛盾的地方；
- 明显的依赖或配置缺口。

除非用户明确要求验证，否则不要执行会修改数据、安装依赖、启动长期运行服务或访问外部系统的命令。

### 6. 输出分析报告

按照下面的固定格式输出。把事实、分析结论和待确认问题分开。重要结论都要附文件路径；涉及代码的结论尽量附行号。

## 报告格式

```markdown

## 1. 项目用途
说明项目解决的问题、主要使用者和本次分析范围。

## 2. 技术栈
| 项目 | 结论 | 证据 |
|---|---|---|
| 编程语言 |  |  |
| 框架 |  |  |
| 包管理器 |  |  |
| 数据库或外部服务 |  |  |

## 3. 目录结构
只列出重要目录和文件，并说明各自职责。

## 4. 运行方式
给出项目中明确记录的安装、配置、启动和测试命令。
没有证据支持的命令必须标注“推断，待验证”。

## 5. 核心入口
列出入口文件、函数或路由，并说明它们如何被触发。

## 6. 主流程
使用编号步骤或 Mermaid 流程图，说明输入如何到达输出。

## 7. 关键模块
| 文件 | 作用 | 关键接口 | 证据 |
|---|---|---|---|

## 8. 配置与依赖
列出环境变量、外部服务、数据文件和启动前置条件。

## 9. 测试与验证
列出已有测试、测试命令和目前尚未验证的部分。

## 10. 风险与待确认问题
只列出有证据支持的问题，并区分“已确认风险”和“待确认问题”。

## 11. 建议阅读顺序
按照入口文件、核心流程、领域模块、测试和配置给出阅读顺序。
```

## 证据规则

- 环境提供项目绝对路径时，使用绝对路径；否则使用清晰的项目相对路径。
- 涉及具体代码的结论，在条件允许时附上行号。
- 没有找到文件、命令、测试或配置时，明确写“未找到”。
- 没有实际执行或确认的命令和结论，明确写“待验证”。
- 不要编造架构分层、接口行为、环境变量或测试结果。
- 不要隐藏文档和实现之间的矛盾。应同时报告两者，并根据证据说明哪一方更可能是当前有效依据。

## 使用边界

- 这是项目分析流程，不是功能实现流程。
- 分析过程中不要编辑、删除、重命名或生成项目文件。
- 不要把猜测的命令写成已验证命令。
- 不要把简短的项目概览扩展成所有文件的无差别罗列。
- 如果项目过大，无法在当前范围内完整分析，应说明已经检查的内容和未覆盖的范围。

## 示例

用户请求：

> 帮我熟悉这个项目，并说明用户请求是怎么得到最终响应的。

应执行：

1. 查找项目约束文件和运行环境配置。
2. 定位服务或 CLI 入口。
3. 跟踪一个请求经过的关键模块。
4. 使用文件路径和代码证据说明调用链。
5. 区分项目中明确记录的启动命令和仍需验证的命令。

## 版本说明

`1.0.0` 是初始版本，包含项目结构梳理、运行环境识别、主流程追踪、运行条件检查和结构化报告输出。

当前版本不包含自动修改代码、自动安装依赖或自动生成回归测试。
